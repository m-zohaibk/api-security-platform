# crAPI Verification Summary

**Repository:** [`m-zohaibk/api-security-platform`](https://github.com/m-zohaibk/api-security-platform)
**Training target:** [`http://crapi.apisec.ai`](http://crapi.apisec.ai)
**Application:** crAPI, an intentionally vulnerable API training application
**Verification date:** 2026-08-20
**Mode:** Read-only safe mode; no account creation, login state mutation, purchase, feedback submission, or other state-changing action was performed.

## Executive Summary

The improved scanner was tested against crAPI after earlier verification on testasp, DVWA, and DVGA. Discovery identified **51 unique endpoints**. The safe-mode filter retained **42 read-only endpoints** and excluded **9 potentially state-changing or credential-bearing routes**. The final uncapped run used `MAX_ENDPOINTS=100`, so the configured budget did not truncate the 42-endpoint safe inventory.

The final scan produced **zero confirmed vulnerabilities** and a **3.5/100 LOW** score. Its 42 persisted observations were all suspected missing-security-header observations; no SQL injection, XSS, command injection, LFI, BOLA/IDOR, or other active-probe result survived as a non-baseline finding. This matches the independent checks performed against representative SPA-shell routes, which returned the crAPI frontend HTML shell rather than an API response.

The credential endpoint was tested separately with a SQL-injection-shaped login probe. The baseline and probe both returned HTTP 500 with the same 74-byte plain-text response, no token-like output, no error-signature change, and no timing or size evidence of authentication bypass. The scanner therefore did not claim a confirmed credential SQL injection. The raw result is [`tests/crapi_login_manual_sql_results.json`](tests/crapi_login_manual_sql_results.json).

## Scope and Method

Testing remained limited to a public training target selected for security-tool research. The safe-mode policy was implemented in the scanner rather than relying only on an external endpoint list. It retained GET and other read-only routes while excluding login, signup, and routes that appeared to require state changes. The inventory is preserved in [`tests/crapi_discovery_inventory.json`](tests/crapi_discovery_inventory.json).

Each retained endpoint received a baseline request. Active payloads were selected by route and method. API-like JSON endpoints could receive relevant probes, while routes that returned the same frontend SPA shell were identified from the `Content-Type` header and root-marker HTML and were short-circuited before active payloads. A final route-family check covered `/`, `/health`, `/status`, `/search`, `/products`, `/cart`, `/profile`, `/account`, `/dashboard`, `/users/v1/*`, `/books/v1/*`, `/rest/*`, and `/api/*` discoveries.

The 42 remaining observations were generated by the baseline security-header check. They are intentionally not counted as confirmed vulnerabilities. Missing response headers can be a legitimate hardening gap, but the result should be interpreted in the context of the target’s frontend shell and the scanner’s current header policy rather than as evidence of an exploitable API vulnerability.

## Independent Verification

The independent verification used the same target and the same essential proof standard as the scanner: establish a baseline, send a bounded probe, compare status, size, timing, content type, and relevant response markers, and only treat an exploit as confirmed when a concrete proof condition is present.

| Check | Manual result | Scanner result |
|---|---|---|
| Representative crAPI SPA-shell routes | `/api/Feedbacks`, `/users/v1/1`, `/books/v1/book1`, and `/rest/products/search` returned HTTP 200 `text/html` with the frontend root marker. | Shell responses were recognized; active payloads were skipped and no generic injection findings were persisted. |
| Credential SQLi probe | `/identity/api/auth/login` baseline and SQLi-shaped probe both returned HTTP 500, identical 74-byte plain text, no token-like response, and no SQL error signature. | No confirmed credential SQLi; the credential probe maps to the normal `SQL_Injection` proof verifier. |
| Full safe inventory | 42 retained endpoints were reached without the endpoint cap truncating the inventory. | 42 endpoints scanned; zero confirmed vulnerabilities. |

The credential manual artifact is [`tests/crapi_login_manual_sql_results.json`](tests/crapi_login_manual_sql_results.json). The final scan database was `/tmp/crapi_full_safe_final_v5.sqlite` during this verification run.

## Accuracy Issues Found and Fixed During crAPI Testing

| Issue | Effect before the fix | Correction |
|---|---|---|
| Credential/login routes had no dedicated probe path. | Login SQL injection was not explicitly exercised. | Added `SQL_Injection_Credential` with a JSON email/password probe and mapped it to the normal SQLi proof verifier. |
| HTTP 500 responses could be treated as generic security-header evidence. | A broken or unavailable API contract could inflate misconfiguration noise. | Restricted the security-header path so 500 responses do not become header findings solely because they lack headers. |
| API paths returning the frontend HTML shell were treated as APIs. | Generic SQLi, XSS, command, and LFI syntax generated suspected false positives. | Added case-normalized SPA-shell detection and extended it across API, identity, users, books, REST, v1, and v2 route families. |
| GET-only routes received POST XSS probes. | HTTP 405 responses created unnecessary active-probe noise. | XSS probe method now follows the endpoint’s method; 405 responses are blocked from vulnerability proof. |
| Baseline shell routes still entered the generic active queue. | The scanner spent requests on probes that could not reach an API handler. | Added baseline shell short-circuiting before active payload dispatch. |
| Generic suspicion was easy to confuse with proof. | Payload syntax alone could look like a vulnerability in reports. | Confirmed counts remain proof-gated; suspected findings retain explicit “without proof” wording. |

## Limitations and Next Steps

This result is a safe-mode assessment of unauthenticated or publicly reachable behavior. It does not establish the security of authenticated crAPI workflows, object authorization, business logic, JWT handling, rate limits, mass assignment, or state-changing actions. The excluded nine routes require a controlled authenticated workflow and should be tested only with a disposable account, explicit authorization, and transaction-safe cleanup.

The current SPA-shell detector is deliberately conservative: it suppresses active testing when the baseline is clearly a frontend shell, but it does not replace API specification discovery or authenticated session handling. Future work should add OpenAPI-driven parameter extraction, authenticated scan profiles, differential response analysis for blind injection, per-route response fingerprints, and explicit rate-limit and authorization test plans.
